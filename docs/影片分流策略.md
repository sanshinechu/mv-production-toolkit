## 一句話

影片提示詞三方共審「無意見」之後，**整支 MV 選一條路**：
🅰 Colab H3（Claude／Codex／Antigravity 皆可代跑，用 Colab A100）、🅱 Google Flow（老師在 Flow 平台自己生）、🅲 Magnific（Claude／Codex／Antigravity 皆可代跑，扣 Magnific 點數，內含 Kling／Veo／Seedance／Wan 等模型），或 🅳 Kling.ai（Claude／Codex／Antigravity 皆可代跑，扣 Kling 官方帳號點數，有 Kling 4.0 與 Element 鎖角色）。
四條路的成品都放到同一個地方、同一套檔名，組裝不必分來源；也可以**主路線以外的個別鏡頭用 🅲 或 🅳 補生**（例如 H3 生不好的那一鏡）。

```
影片提示詞（mv-06）── cowrite --flow mv（審核模式）──「無意見」
        │
  整支 MV 選一條路線
        ├─ 🅰 Colab H3：Claude 寫 H3 分鏡 → 三方審核 → 拆檔＋機器檢查 → 首幀組圖審查 → 清單給老師

        └─ 🅳 Kling.ai：Claude 建 Element、選模型、上傳首幀 → 清單（點數待實測）
              → 老師說「直接生影片」→ 最難一鏡＋量點數 → 整批 → 下載改名放進 videos-raw/
        │
  collect_videos.py --check：每鏡都有、秒數夠、1080p、24 fps
                     ↓
       make_mv.py --videos 組裝（再擋一次解析度／fps）→ review_mv.py
                     ↓
       ⛔ 抽幀停損點：三家各自看 pass1／cuts 兩張圖都說 OK 才算完成

## 共同約定（四條路都一樣）

| 項目 | 規定 |
|---|---|
| 成品位置 | `outputs/<MV名>/videos-raw/` |
| 檔名 | `cutNN_<英文短名>.mp4`，NN 對齊分鏡表（mv-11）的 cut 編號；同一鏡重生就覆蓋，舊的自己移到 `videos-raw/_old/` |
| 規格 | 1920×1080、24 fps；秒數 **≥ 分鏡表該鏡秒數**（多的組裝時裁掉，不夠會被擋下） |
| 聲音 | H3／Veo／Kling／Seedance 都可能自己配聲音，**組裝時一律丟掉**，只用歌曲；🅲 生成時就關掉音效（`withSoundEffects: false`），能省點數；🅳 有 `enable_audio` 參數的模型一律給 `false`（預設是 `true`） |
| 角色一致 | 首幀用 mv-04／05 的單張分鏡圖；角色參考用 mv-02 的**單張半身參考圖**，不要拿左右分割的定妝圖（會被照抄成拼貼） |
| 6 項原則 | [影片製作基本原則](影片製作基本原則.md) 照舊適用 |

## 🅰 Colab H3 路線（Claude／Codex／Antigravity 皆可代跑）

> **誰能跑**：Claude、Codex、Antigravity 都可以（2026-10-18 老師確認）。三家都透過 `scripts/colab_bridge.py` 用命令列操作瀏覽器裡的 Colab，不靠各自的 Colab MCP（見記憶 colab-mcp-account-and-tab）。2026-10-09 曾查到 Codex Desktop 的 Colab MCP 是 `Unsupported`，當時寫成「只有 Claude 能接手」，但 colab_bridge.py 是命令列工具，不受這個限制。
> **成品一定要落地**：Colab 的 `/content` 是暫存，換執行階段就清空。`h3_batch.py` 的輸出直接寫進雲端 `colab_mv/outputs/`，再用 `collect_videos.py` 搬回專案；10/09 用 video maker.ipynb 生在 `/content/ComfyUI/output/` 的 H3 測試片沒有存到雲端，執行階段已換過，視為已遺失。

1. **Claude 寫 H3 分鏡初稿**：把定案的影片提示詞逐鏡轉成一份 Markdown（總表＋每鏡 `### cutNN` 加一個 ```json 區塊），格式與欄位規則照 `15_ai共筆工作流/flows/specs/H3分鏡.md`。重點：
   - `size` 一律 `[1344, 768]`（H3 原生短邊 768，32 的倍數，接近 16:9）。
   - `duration` = 分鏡秒數＋0.5 秒餘裕，**上限 12 秒**（超過會飄）；更長的鏡頭拆兩鏡或改用 Ken Burns。
   - 首幀檔名 `cutNN_first.png`；需要尾幀才加 `last_frame`（首尾幀同空間）。
   - 角色描述逐字沿用主角造型的一致性參考詞，`style` 全片逐字相同。
2. **三方審核「H3 分鏡」**（2026-10-10 老師要求加的關卡——這步要翻譯又要拆格式，最容易偏離原意）：
   ```
   python cowrite.py "<MV名> H3 分鏡" --flow mv-h3 --from "<影片提示詞那份共修>" --draft <H3 分鏡初稿.md>
   ```
   三家逐鏡比對影片提示詞（忠實、編號、秒數、JSON 合法、一致性、放大方式、禁忌），一整輪「無意見」才交給老師 ok。
3. **拆檔＋機器檢查**：
   ```
   python scripts/h3_specs_from_review.py "<H3 分鏡那份共修>" --mv <MV名> --storyboard outputs/<MV名>/storyboard_vN.md
   ```
   拆成 `colab_mv/inputs/<MV名>/cutNN.json`，同時擋：JSON 格式、欄位規則、秒數對分鏡表、H3 官方六段格式 0 錯誤。**沒過就不寫檔**，把問題當主持人意見 `--resume` 回去再審。通過會印出給老師的清單（第 4 步）。Claude 再把分鏡圖改名 `cutNN_first.png` 放進同一個資料夾（清單上「首幀檔在嗎」全打勾才算齊）。

   **3.5 首幀組圖審查**（2026-10-30 加。編號用 3.5 而不是插新號，因為 mv-05、`H3分鏡.md`、`h3_specs_from_review.py` 都寫著「🅰 第 4、7 步」，重新編號會讓那些交叉引用全部失準）

   第 3 步只檢查檔案「在不在」，第 2 步的三方審核只看得到文字。**道具提前出現、服裝狀態接不上、不可逆的東西又復原**這幾類錯，只有把首幀排開來看才抓得到。理由很實際：**改一張圖幾十秒，重生一支影片要好幾分鐘，還吃運算單元。**

   1. 把 `colab_mv/inputs/<MV名>/` 的 `cutNN_first.png` **依鏡號排序拼成總覽圖**，沿用 `mv-12` 既有的 ffmpeg tile 做法（2x3 或 3x4，見 `mv-12-shots-generator` SKILL），**不用另寫工具**；圖存到 `outputs/<MV名>/review/`。
   2. 對著 **mv-11 分鏡表的「資產狀態」欄**與 **mv-13 區塊三的資產狀態表**逐格核對：
      - 這一鏡該有、不該有的道具與服裝狀態對不對
      - 有沒有東西**提前出現**（例如笑點的關鍵物在前一鏡就露出來）
      - 有沒有違反**不可逆事項**（已落下的鐵門又回到上面、脫掉的外套又穿回身上）
      - 角色外觀前後一致、沒有多出人、沒有亂碼字
   3. ⚠️ **這一關必須由看得到圖的一方做**：cowrite 只把文字傳給三家，**看不到圖**（見記憶 `cowrite-review-before-teacher`）。要嘛 Claude／Codex／Antigravity 各自在自己環境開圖，要嘛老師目視；**不能把文字共審通過當成圖片驗收通過**。
   4. **只修有問題的那一張，其他鏡頭不要動** —— 重做整組，原本對的地方也可能被改壞。修完再看一次。
   5. **首幀沒過的鏡頭先不要送去生成**：起點錯了，後面全錯。
   6. 一般 MV（沒有 mv-13 資產狀態表）也值得跑這一關，只是核對依據只有分鏡表的「畫面」欄。
   7. ⚠️ **這一關擋的是跨鏡狀態錯**。一鏡之內的動態錯（中途變形、轉身換人、動作方向反了）首幀看不出來——《半張車票》的 `cut49` 外套突變、`cut40` 鐵捲門反向就是這類，要留到組裝後的 `review_mv.py` 抽格與交件前抽幀；源頭則靠把方向與不可逆寫進 `action`（mv-11 資產狀態欄 → mv-06／H3 分鏡）。
4. **給老師看的清單**：每鏡秒數、首幀、放大方式、預估時間、預估運算單元（A100 約 6.77／小時）。**老師說「直接生影片」才跑。**
   - 預估時間用〈雨夜404檔案〉（2026-10-11，47 鏡）的實測：H3 每鏡約 150～340 秒，FlashVSR 放大每鏡約 290～440 秒，**一鏡合計約 7～13 分鐘**，47 鏡要跑好幾個小時。
   - 🔀 **「放大方式」那一欄是要老師選的，不要一律填 `flashvsr`**（2026-10-30 老師定）。逐鏡標出建議與理由，讓老師在說「直接生影片」時一併定下來：
     - **對嘴鏡、臉部特寫** → 建議 `lanczos`（不改畫面、保住嘴型，但比較糊），或 `flashvsr` 但清單上註明「要逐鏡抽格看臉」。
     - **全景、風景、沒有人臉的鏡頭** → `flashvsr`（會多畫細節，這類鏡頭影響小）。
     - 哪幾鏡是對嘴／特寫，照 mv-11 分鏡表與「最難一鏡」那行判斷；分不出來就在清單上問，不要自己決定。
   - ⚠️ A100 上**沒有「不改內容又清楚」的選項**：只有 `flashvsr`（清楚但會改）或 `lanczos`（不改但糊）。要兩全得等別的升頻方式驗過（候選見 `參考比對_DSLab研習` 的 H3 進階 A3「後製升頻」LoRA，**未實測**）。
   - 靜態分鏡圖那一層的放大是另一回事（可用 RTX VSR、Upscayl 等），正本在 `mv-05` skill，這裡不抄。
5. **先做「最難一鏡」**（mv-11 分鏡表下方標的那一鏡）：`h3_batch.py inputs/<MV名> --only cutNN`，生完給老師看；角色不像、多出人、亂碼字這類共通問題在這一鏡解決，再跑整批。
6. **批次生成**：用 `scripts/colab_bridge.py` 接手 Colab → `setup_comfy.py --pack h3 upscale` → **一律用三合一守護啟動**（2026-10-26 老師定的標準，不要直接叫 `h3_batch.py`）：
   ```
   !python /content/drive/MyDrive/colab_mv/tools/h3_guard.py /content/drive/MyDrive/colab_mv/inputs/<MV名> --only cutNN ...
   ```
   放在**前景儲存格**執行，它會做三件事：
   - **斷點續跑**：背景 nohup 啟動 `h3_batch.py`（已有 `clip_1080p.mp4` 的鏡跳過、只有 `clip.mp4` 的只補放大）；批次程序中途結束但還有鏡沒完成，自動續跑（預設最多 2 次）。
   - **防休眠**：每 60 秒印一次「完成幾鏡／正在跑哪鏡／程序是否活著／還剩哪些」，保持輸出串流活躍。只能減少前景閒置斷線，**擋不住** Colab 單次執行上限和分頁被關，長批次仍要留著分頁。
   - **自動釋放 GPU**：所有目標鏡都有 ffprobe 驗過 1920×1080 的 `clip_1080p.mp4` 後，自動 `runtime.unassign()`。續跑用完仍有缺鏡，也會印出缺哪幾鏡後釋放（不讓 A100 閒置扣點）；要保留連線加 `--keep`。
   - ⚠️ **「完成」只看檔案在不在，不看 `progress.json`**：progress.json 會留著上一輪的 `done`（10-26 重生 19 鏡時，沒跑到的 11 鏡照樣顯示 done，被誤報成「已生成完」）。要重生某鏡，先把該鏡的 `clip*.mp4` 移到 `cutNN\_old_<日期>\`，不然會被跳過。
   - 回報「生完」之前，自己先數一次 19 張 `clip_1080p.mp4` 的檔案時間都是這一輪的，不要只看守護或 progress 的訊息。卡住就 pkill 重跑，見記憶 colab-stuck-kill-and-retry。
7. **放大到 1080p**（`tools/upscale.py`，h3_batch 生完自動做）：**A100 上可選 `flashvsr` 或 `lanczos`**，每鏡分鏡 JSON 都要明寫，照第 4 步老師選的填。

   | `upscale` | 會不會改畫面 | 什麼時候選 |
   |---|---|---|
   | `"flashvsr"` | 會多畫細節，可能改臉與嘴型 | 預設；全景、風景、沒有人臉的鏡頭 |
   | `"lanczos"` | 不改畫面，但比較糊 | 對嘴鏡、臉部特寫要保住嘴型時 |
   | `"rtx"` | 不改內容 | ⛔ **A100 上不能用**（見下），只給本機 RTX 顯卡手動跑 `upscale.py --method rtx` |
   - **RTX VSR 在 A100 上跑不起來**：〈雨夜404檔案〉（2026-10-11）47 鏡裡標 `rtx` 的 26 鏡全部 `upscale_failed`，錯誤都是 `NvVFXError: NvVFX_Load failed: The requested feature or capability was not found (code -14)`；標 `flashvsr` 的 21 鏡全部成功。RTX VSR 是給 RTX 系列顯卡用的，A100 是資料中心卡，推測是這個原因。那 26 鏡後來另外補出了 1080p／24 fps 的檔案，但當天筆記沒記用哪種方法補的。
   - ✅ **工具預設是 `flashvsr`（2026-10-18）**：`h3_batch.py` 沒寫 `upscale` 就用 flashvsr、`upscale.py --method` 預設 flashvsr。`h3_specs_from_review.py` 拆檔時**收 `flashvsr` 與 `lanczos`、遇到 `rtx` 直接退回**（2026-10-30 放寬，原本只收 flashvsr，導致第 4 步選了 lanczos 也拆不出檔）。`upscale.py --method rtx` 還留著，只給本機 RTX 顯卡手動用。
   - FlashVSR 會多畫一點細節，**近景臉部一定要逐鏡抽格看**；看了不行就把那幾鏡改 `"lanczos"` 重跑。
   - 已經失敗或要換放大方式的鏡頭，重跑 `h3_batch.py` 會自動「只補放大」；先把那幾鏡 JSON 的 `upscale` 改成要用的那個再重跑。
8. **搬回專案**：`python scripts/collect_videos.py <MV名> --storyboard <storyboard_vN.md>` 把 `colab_mv/outputs/<MV名>/cutNN/clip_1080p.mp4` 複製成 `outputs/<MV名>/videos-raw/cutNN_*.mp4`。
9. 用完 `runtime.unassign()` 斷線（用 `h3_guard.py` 啟動的會自動做；手動跑的要自己做）。

## 🅱 Google Flow 路線（走 `flow_auto.py` 自動化，Claude／Codex／Antigravity 皆可代跑）

> **2026-10-30 老師定：選 🅱 就是用 `scripts/flow_auto.py` 跑，不再手動逐鏡點。**
> 它用 Playwright 操作**本機 Chrome**，所以要在「已經 `login` 過的那台」跑；
> 登入狀態存在本機 `%LOCALAPPDATA%\flow_auto\chrome_profile`（**不放 Drive**），
> 所以**每台要各自讓老師 `login` 一次**，程式不碰帳密。

1. **Flow 提示詞共審**：
   ```
   python cowrite.py "<MV名> Google Flow 提示詞" --flow mv-flow --from "<影片提示詞那份共修的資料夾名>"
   ```
   `--from` 把前面已定案的劇情、角色、場景、影片提示詞帶進來當背景，三家只審 Flow 提示詞本身。規格見 `15_ai共筆工作流/flows/specs/Google Flow提示詞.md`。
2. **老師登入一次**（只有這步要老師動手，而且同一台只要做一次）：
   ```
   python scripts/flow_auto.py login
   ```
   會開一個專用 Chrome，老師自己登 Gmail；看到「新增專案」就自動結束。
3. **寫 `jobs.json`**（一鏡一筆，照分鏡表）：
   ```json
   [{"cut": "cut04", "first": "<專案>/分鏡圖/cut04_first.png", "prompt": "...", "seconds": 4}]
   ```
   - 要首尾幀的鏡加 `"last": "<專案>/分鏡圖/cut04_last.png"`；**刻意只放首幀要寫 `"last": null`**。

3. **三家都說 OK 才算過**。任何一家指出問題就要處理，不用多數決蓋過；三家判斷不一致時（例如「這鏡到底有沒有動」），用像素差異圖之類的量測定案，不靠再看一次。
4. 有問題：回到該鏡重生（🅰 `h3_batch.py --only cutNN`；🅱 老師重生；🅲 該鏡重跑 `video_generate`；🅳 該鏡用原本的工具重跑（`image_to_video` 或 `omni_ref_video`）；任何路線都可以改用 🅲 或 🅳 補這一鏡）→ 重新 collect → 組裝 → 再回到第 1 步。
5. 通過後在每日筆記記下「抽幀三家已看、日期、各家結論」，作為交件檢查紀錄（6 項原則交件檢查最後一項），之後才進打包／上傳。上傳一律先 `private`，老師說公開才改。上架完成後，老師會把整支片的資料夾移出 `outputs/`，放到當台主機自己的封存位置（各台不同，都有備份到雲端硬碟）；之後要找已上架的片，**不要在 `outputs/` 找不到就判定遺失**，先問老師在哪一台、放在哪裡。
